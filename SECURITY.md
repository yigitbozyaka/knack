# Security policy

Knack takes the security of its users seriously. This document explains how to report a vulnerability, what we'll do with the report, and what's in / out of scope.

## Supported versions

Knack is shipped from a single trunk. We provide security fixes for:

| Version              | Supported       |
| -------------------- | --------------- |
| `master` (latest)    | ✅ yes          |
| `dev` (integration)  | ✅ yes          |
| Older tagged commits | ❌ no — upgrade |

If you self-host an older revision, please update before reporting. We'll happily review reports against current `master`.

## How to report a vulnerability

**Email [security@knack.wtf](mailto:security@knack.wtf).**

Please **do not** open a public GitHub issue, file a discussion, or post about the vulnerability anywhere public until we've shipped a fix and you've coordinated disclosure with us.

If you'd like to encrypt your report, request our PGP key in your first message and we'll send it before you share details.

A useful report includes:

- A short description of the issue and what an attacker could do with it
- Steps to reproduce — ideally a minimal test case
- The affected URL, route, or commit hash
- Any logs, payloads, or screenshots (redact your own personal data)
- Your name / handle if you'd like to be credited (see [Hall of fame](#hall-of-fame))

## What you can expect from us

- **Initial reply within 5 business days.** Usually much faster, but 5 days is the floor we'll commit to.
- **Triage and assigned severity** as soon as we've confirmed the issue.
- **Status updates** at least once a week while the fix is in progress.
- **Credit on disclosure** if you want it (see below).
- **No legal action** against good-faith researchers who follow this policy.

## What's in scope

- The hosted app at [knack.wtf](https://knack.wtf) and any of its subdomains we operate.
- The code in this repository (`github.com/yigitbozyaka/knack`).
- Vulnerabilities introduced by our dependencies that are exploitable in our context (please confirm exploitability before reporting; "this transitive dep has a CVE" without an attack path is noise).

Examples of issues we want to hear about:

- Auth or session handling flaws
- Injection of any kind (SQL, command, XSS, SSRF, prototype, template)
- Insecure file upload / storage / serving
- Path traversal, race conditions, IDOR, broken access control
- Cryptographic mistakes (weak hashing, predictable tokens, key leakage)
- Vulnerabilities in our CI/CD that could compromise releases or supply chain
- CSP / security-header bypasses that lead to a real exploit

## What's out of scope

- Denial of service at the network layer (handled upstream by Cloudflare / Vercel / our hosting provider).
- Vulnerabilities requiring a malicious browser extension, a rooted device, or physical access.
- Reports generated by automated scanners with no demonstrated exploit (if your report is "scanner X says Y", we'll close it).
- Best-practice nits without a real attack ("you're missing `X-Permitted-Cross-Domain-Policies`", etc.) — open a regular issue or PR for those.
- Rate-limit gaps that would only enable brute force against unauthenticated public utility endpoints (we still want to know, but they'll be triaged as enhancements, not vulnerabilities).
- Self-XSS, clickjacking on pages with no sensitive actions, missing best-practice email DMARC alignment.
- Vulnerabilities in third-party services we use (report those to the vendor; if it impacts us, please tell us too).

## Disclosure

We follow **coordinated disclosure**. Once a fix has shipped to `master` and (where applicable) our hosted environment, we'll publish a write-up — short, honest, and crediting the reporter unless asked not to.

If we can't reach an agreement on disclosure timing within a reasonable window (target: 90 days from your report), we'll work with you on a path forward rather than ignore you. Please don't surprise-publish; we'd rather collaborate.
